IMPLEMENT VALIDATED GENERIC RESEARCH QUERY STRATEGY

PURPOSE

Retrieval Bake-off 01 established:

Current Tavily:
5/7 events found
71.4% retrieval recall

Improved generic Tavily:
7/7 events found
100% retrieval recall

Improved generic Exa:
7/7 events found
100% retrieval recall

Decision:
A — QUERY CONSTRUCTION IS PRIMARY BOTTLENECK

Exa produced cleaner/faster results but provided ZERO incremental event
coverage over improved Tavily.

Therefore:

IMPLEMENT the validated generic query-construction improvement into
JYRA's normal Tavily research path.

DO NOT integrate Exa.

DO NOT change provider routing.

IMPORTANT:

The bake-off allowed up to 2 improved queries.

Production behavior must NOT blindly execute 2 searches for every
research question.

Implement:

→ evaluate retrieval sufficiency
→ QUERY 2 only when necessary.

7. DO NOT CREATE INTENT-LADEN QUERIES
==================================================

Queries must search for observable events.

Do NOT search for conclusions such as:

"[company] needs managed SOC"

"[company] buying cybersecurity"

"[company] looking for managed security provider"

"[company] purchase intent"

"[company] likely to buy SOC"

JYRA searches for EVENTS and FACTS.

Opportunity interpretation happens downstream.

==================================================

Normal flow:

ResearchQuestion

↓
evaluate RETRIEVAL SUFFICIENCY

Do not immediately execute the fallback query.

==================================================
9. RETRIEVAL SUFFICIENCY GATE
==================================================

Implement a deterministic/conservative sufficiency assessment.

The purpose is NOT to decide whether an opportunity exists.

It only decides:

"Do we have enough potentially relevant evidence to avoid another
search?"

Possible statuses:

SUFFICIENT_RETRIEVAL

INSUFFICIENT_RETRIEVAL

PROVIDER_FAILURE

AMBIGUOUS_RETRIEVAL

==================================================
10. WHAT COUNTS AS SUFFICIENT RETRIEVAL
==================================================

Retrieval can be considered sufficient when the primary search returns
one or more credible results materially relevant to the research
question.

Consider observable characteristics such as:

correct entity match

question-category relevance

event-oriented title/snippet/content

credible source

reasonable temporal relevance

Do NOT require a signal to exist.

Do NOT require a fact to be approved.

Do NOT infer purchase intent.

Example:

Research question:
Has Company X recently expanded cybersecurity hiring?

Result:
Official careers page containing security vacancies.

That can be sufficient retrieval.

==================================================
11. WHAT DOES NOT COUNT AS SUFFICIENT
==================================================

Do not consider retrieval sufficient merely because Tavily returned
results.

Examples:

company homepage

generic About page

generic security marketing page

seller/vendor content

wrong entity

generic LinkedIn profile with no question-relevant event

irrelevant result

stale unrelated content

keyword coincidence

Result count > 0 is NOT sufficient by itself.

==================================================
12. FALLBACK QUERY TRIGGER
==================================================

Execute FALLBACK_QUERY only when:

PRIMARY_QUERY completed successfully

AND

retrieval status is:

INSUFFICIENT_RETRIEVAL
or
AMBIGUOUS_RETRIEVAL

Do not use fallback to compensate for provider outage.

Provider errors must follow existing retry/error behavior.

==================================================
13. FALLBACK QUERY BEHAVIOR
==================================================

Fallback must be a generic semantic variation.

It may:

broaden terminology
use alternate role terminology
use alternate event terminology
reduce overly restrictive terms
change query structure

It must NOT:

use benchmark labels
use reference event text
use known answer URLs
use known event-specific person names
brute-force many query variations

Maximum:

2 Tavily search queries per ResearchQuestion in this milestone.

==================================================
14. STOP CONDITION
==================================================

After fallback query:

STOP retrieval for that ResearchQuestion.

Do not recursively generate more queries.

Maximum:

PRIMARY = 1
FALLBACK = 1

TOTAL <= 2 Tavily calls per question.

18. ENTITY SAFETY
==================================================

Improved Tavily produced wrong-entity results in the bake-off.

Therefore query recall improvement MUST NOT weaken entity validation.

Every retrieved result must retain entity-match evaluation.

Wrong-entity results:

may remain in raw retrieval diagnostics

but MUST NOT become accepted buyer evidence.

Do not change entity thresholds in this milestone.

==================================================
19. SELLER VS BUYER SAFETY
==================================================

Preserve existing rule:

seller/vendor/service marketing content must not become buyer-event
evidence.

Example:

A cybersecurity provider advertising Managed SOC does NOT mean that
provider is buying Managed SOC.

Query improvements must not weaken this protection.
